## 三、实验整体逻辑分析

### 3.1 本章节的逻辑主线

本实验围绕“如何让一段内核程序在模拟的 RISC-V 计算机上获得控制权并输出信息”展开。它尚未实现完整操作系统，而是建立后续实验所需的最小运行基础。

需要区分两条相互配合的过程：一条是在宿主环境中把源码加工成镜像的构建过程；另一条是在 QEMU 中从 CPU 复位到执行内核的启动过程。

```text
构建过程：
C / 汇编源码 → 交叉编译生成目标文件 → 按 kernel.ld 链接
           → bin/kernel（ELF）→ objcopy → bin/ucore.img

本次配置的启动过程：
QEMU 初始化并装入固件、内核镜像
  → 从 0x1000 处的复位启动代码开始执行
  → 准备启动参数，取得 0x80000000 作为跳转目标
  → OpenSBI 固件执行初始化并移交控制权
  → 0x80200000：kern_entry
  → 设置内核栈 → kern_init
  → 清零 BSS 对应区间 → cprintf 输出 → 无限循环
```

这里的 `0x1000` 是本次 QEMU 平台观察到的复位入口，不是所有 RISC-V 机器都必须采用的统一地址。`0x80000000` 是本次固件基址，`0x80200000` 是本项目链接脚本指定的内核基址和实际入口地址，三者承担不同职责。

### 3.2 功能的逐步实现与依赖关系

1. **确定内存布局与入口。** 链接脚本将内核安排在 `0x80200000`，并通过 `ENTRY(kern_entry)` 指定 ELF 入口。镜像装入地址必须与程序所依据的链接布局配合，否则地址引用和跳转可能不正确。
2. **编译链接并生成镜像。** 交叉工具链生成 RISC-V 指令，而非宿主机指令。ELF 保留调试所需的符号等信息，原始镜像供本次 QEMU loader 装入内存。
3. **由复位代码转入固件。** 复位时没有通常应用程序的运行环境，需要平台启动代码准备参数并跳转到固件。
4. **由固件转入内核。** OpenSBI 完成其负责的底层初始化和控制权交接。本次用内核入口断点验证交接结果，而非逐条跟踪全部固件指令。
5. **建立内核自己的栈。** C 函数调用和寄存器保存依赖有效栈，因此必须在进入 `kern_init` 前设置 `sp`。
6. **完成 C 层初始化并提供输出。** 初始化代码按链接符号清理 BSS 对应区域，再通过格式化输出和 SBI 服务打印启动信息，为后续实验提供可观察结果。

### 4.1 功能模块：最小内核的构建、入口与输出

**负责人：** 待补充实际学号、姓名。

#### 模块功能描述

本模块涉及以下入口、函数与文件；本次主要阅读和验证这些已有实现，没有可证实的新函数修改。

```c
/* 汇编入口标签：kern_entry，不是普通 C 函数 */
int kern_init(void) __attribute__((noreturn));
int cprintf(const char *fmt, ...);
int vcprintf(const char *fmt, va_list ap);
void cons_putc(int c);
void sbi_console_putchar(unsigned char ch);
uint64_t sbi_call(uint64_t sbi_type, uint64_t arg0,
                  uint64_t arg1, uint64_t arg2);
```

**（1）构建与链接。** Makefile 调用交叉编译器和链接器，使用 `-g` 保留调试信息，使用 `tools/kernel.ld` 控制链接。生成 `bin/kernel` 后，通过 `objcopy --strip-all -O binary` 生成 `bin/ucore.img`，并输出 `obj/kernel.asm` 与 `obj/kernel.sym` 供分析。

链接脚本的关键设置如下：

```ld
OUTPUT_ARCH(riscv)
ENTRY(kern_entry)
BASE_ADDRESS = 0x80200000;
```

脚本从基址开始布置 `.text` 和 `.rodata`，对齐后布置 `.data`、`.sdata` 和 `.bss`，并定义 `edata`、`end` 等符号。ELF 中的入口声明和实际节布局需要共同正确；仅声明入口名称并不能代替正确放置入口代码。

本次已检查符号文件给出的布局为：

| 符号或区域 | 地址 | 用途 |
|------------|------|------|
| `kern_entry` / `.text` 起点 | `0x80200000` | 内核入口与代码区域起点 |
| `kern_init` | `0x8020000a` | C 初始化函数入口 |
| `.rodata` 起点 | `0x802004c8` | 只读数据 |
| `bootstack` / `.data` 起点 | `0x80201000` | 内核栈预留区域起点 |
| `bootstacktop` | `0x80203000` | 初始内核栈指针所用地址 |
| `edata`、`end` | 均为 `0x80203008` | 本次构建中 BSS 对应清零区间长度为 0 |

上述地址属于本次构建，后续改变源码和链接结果后可能变化。其中栈顶、内核入口也得到用户调试文本中的符号查询支持。

**（2）汇编入口。** `kern/init/entry.S` 先建立栈，再转入 C 代码：

```asm
kern_entry:
    la sp, bootstacktop
    tail kern_init
```

栈由 `.space KSTACKSIZE` 预留，`KSTACKSIZE` 为两个 4 KiB 页，即 8 KiB。符号差值 `0x80203000 - 0x80201000 = 0x2000` 与此相符。

**（3）C 层初始化。** `kern/init/init.c` 中的主要逻辑为：

```c
extern char edata[], end[];
memset(edata, 0, end - edata);
const char *message = "(THU.CST) os is loading ...\n";
cprintf("%s\n\n", message);
while (1)
    ;
```

`edata` 和 `end` 来自链接脚本，初始化代码清零二者之间的区域，以建立未显式初始化静态存储对象应有的零值环境。本次符号文件中二者相同，说明该构建的清零长度为 0；不能声称本次观察到了非空 BSS 数据被逐项清零。保留这段逻辑仍为将来增加 BSS 对象提供初始化支持。

输出后无限循环与 `noreturn` 属性相配合。终端保持在启动信息处，不意味着内核卡在异常中，而是符合本程序的预期行为。

**（4）格式化打印与 SBI 服务。** 按源码，输出经过以下调用关系：

```text
cprintf → vcprintf → vprintfmt → cputch
        → cons_putc → sbi_console_putchar → sbi_call → ecall
```

`vprintfmt` 解析格式串并调用字符输出回调。`cons_putc` 将字符传给 `sbi_console_putchar`；后者使用本项目的旧版 SBI 控制台输出服务。`sbi_call` 将服务编号放入 `a7`，参数放入 `a0`～`a2`，执行 `ecall`，再从 `a0` 取返回值。这是本实验内核请求固件服务的路径，不应与用户程序向内核发起系统调用混为一谈。

该调用关系是源码层面的逻辑关系。由于构建启用了优化，运行时反汇编可能出现内联或其他变化，不保证每层都保留独立函数调用指令。

### 4.2 练习 1：理解内核启动中的程序入口操作

**负责人：** 待补充实际学号、姓名。

#### （1）`la sp, bootstacktop` 完成什么操作？目的是什么？

`la` 是装入地址的汇编伪指令。该语句将符号 `bootstacktop` 对应的地址放入栈指针寄存器 `sp`，而不是从栈顶内存中读取一个数据值。

在进入内核时，`sp` 仍可能指向固件使用的栈。本次在内核入口处观察到 `sp = 0x8001bd80`。这条指令为内核建立自己的栈环境，使后续 C 代码能够按照调用约定保存返回地址、寄存器和局部数据。栈向低地址增长，因此最初将 `sp` 设置为预留栈区域的高地址边界。

本次查询结果：

```text
(gdb) p/x &bootstacktop
$1 = 0x80203000
(gdb) info registers sp
sp             0x8001bd80       0x8001bd80
```

入口反汇编显示伪指令展开为：

```asm
0x80200000 <kern_entry>:   auipc sp,0x3
0x80200004 <kern_entry+4>: mv    sp,sp
```

`auipc sp,0x3` 将当前指令地址加上 `0x3 << 12`，计算得到 `0x80203000`。第二条显示为 `mv sp,sp`，是本次低位偏移为 0 时的反汇编别名，相当于 `addi sp,sp,0`。

实际记录中，执行一次 `si` 后 PC 到达 `0x80200004`，说明第一条真实指令已执行；之后直接 `continue`。因此可以依据指令语义推导设置后的栈地址，但记录没有再次查询 `sp` 来直接显示该值。本报告不把推导值写成已保存的寄存器观察。

#### （2）`tail kern_init` 完成什么操作？目的是什么？

`tail` 是尾调用伪指令，在不建立新的返回地址的情况下将控制权移交给目标函数。当前构建中反汇编为：

```asm
0x80200008 <kern_entry+8>: j 0x8020000a <kern_init>
```

其目的在于从最少量的汇编准备代码进入 C 语言初始化逻辑。这里不需要像普通可返回函数调用那样保存返回到入口的地址，因为 `kern_init` 声明为不返回，并以无限循环结束。入口汇编的职责是准备好栈并完成控制权移交，而不是在初始化结束后继续处理。

本次未单独单步停在 `kern_init` 第一条指令；入口反汇编证明其跳转目标，终端中出现由 `kern_init` 调用打印的字符串，则提供程序确实继续进入 C 初始化输出路径的运行证据。

#### （2）最初几条指令位于什么地址？分别做什么？

连接后得到：

```text
0x0000000000001000 in ?? ()
(gdb) info registers pc
pc             0x1000   0x1000
```

因此，本次模拟平台从 `0x1000` 开始执行。初始反汇编及其作用如下：

| 地址 | 指令 | 功能及实际状态 |
|------|------|----------------|
| `0x1000` | `auipc t0,0x0` | 将当前 PC 加 0 放入 `t0`；单步后 `t0=0x1000` |
| `0x1004` | `addi a1,t0,32` | 计算启动参数指针；单步后 `a1=0x1020` |
| `0x1008` | `csrr a0,mhartid` | 读取当前硬件线程编号；单步后 `a0=0` |
| `0x100c` | `ld t0,24(t0)` | 从 `0x1018` 读取 64 位跳转地址；单步后 `t0=0x80000000` |
| `0x1010` | `jr t0` | 按 `t0` 中的地址转移控制，即转到 `0x80000000` |

这些指令主要进行地址计算、启动参数准备以及到固件的跳转，并非已经开始执行内核。在这段短代码中，`a1` 指向复位区域后的参数数据；本次没有解析 `0x1020` 处内容，因此不能仅凭该寄存器值进一步声称已经验证了完整设备树结构。

`x/10i $pc` 还将 `0x1014` 及后续位置显示为 `unimp` 等内容。这是将连续内存按指令解码的结果，后续区域包含数据；正常控制流在 `0x1010` 已跳转，不会顺序执行所有被显示的条目。不能将这些反汇编显示直接视为非法指令异常证据。

#### （3）单步观察过程

以下表格概括完整会话中实际记录的关键状态：

| 观察时刻 | PC | 关键寄存器或结果 |
|----------|----|------------------|
| 刚连接 | `0x1000` | 停在第一条复位指令 |
| 第一次 `si` 后 | `0x1004` | `t0=0x1000` |
| 第二次 `si` 后 | `0x1008` | `a1=0x1020` |
| 执行 `csrr` 后 | `0x100c` | `a0=0` |
| 执行 `ld` 后 | `0x1010` | `t0=0x80000000` |
| 设置断点并继续后 | `0x80200000` | 命中 `kern_entry` |
| 内核入口单步一次后 | `0x80200004` | 下一条指令为 `mv sp,sp` |

GDB 的箭头指向下一条将执行的指令。例如停在 `0x1008` 时，读取 `mhartid` 的指令尚未执行，需要再执行一次 `si` 才能将其结果视为此次读取所得。

本次从 `0x1010` 直接使用 `continue` 运行到内核入口，并没有单独保存 `PC=0x80000000` 的停点。因此，固件入口地址由加载到 `t0` 的值、`jr t0` 的语义以及终端 A 显示的 Firmware Base 相互印证；不是一次已保存的固件入口断点观察。

#### （4）内核第一条指令的验证

执行：

```gdb
break *0x80200000
continue
info registers pc
x/6i $pc
info address kern_entry
```

真实输出中的关键内容为：

```text
Breakpoint 1, kern_entry () at kern/init/entry.S:7
7           la sp, bootstacktop
pc             0x80200000       0x80200000 <kern_entry>
=> 0x80200000 <kern_entry>:     auipc   sp,0x3
   0x80200004 <kern_entry+4>:   mv      sp,sp
   0x80200008 <kern_entry+8>:   j       0x8020000a <kern_init>
```

这个结果同时说明：CPU 已经到达预期内核地址；GDB 将该地址解析为 `kern_entry`；第一条机器指令是 `la sp, bootstacktop` 的展开部分。启动流程已从复位路径推进到内核第一条指令。

`info address kern_entry` 同时显示 `in a file compiled without debugging`，但本会话已能定位到 `entry.S:7`，且地址和反汇编均可读取。不能据这一条符号描述就断定整个 ELF 没有调试信息或此次调试失败。

#### （5）镜像加载与控制权交接的区别

指导书给出使用 `watch *0x80200000` 观察内核装入的提示，但本次 Makefile 通过 QEMU generic loader 在启动阶段装入 `bin/ucore.img`。因此，镜像数据装入与 CPU 随后执行到该地址是两件不同的事。在 GDB 连接后设置写监视点，不保证能捕获此前已经完成的镜像装入。

本次实际使用执行断点验证控制权到达内核，没有设置或命中该写监视点，也没有证据表明 OpenSBI 在本次运行中重新复制了整个内核镜像。报告据此使用“QEMU 装入镜像，固件移交控制”的描述。

### 4.4 Challenge 与拓展

本次已核对的 Lab1 练习页列出两项正式练习，没有独立的必做 Challenge。页面关于现代笔记本启动的内容可作为拓展理解：PC 通常经过 UEFI 固件、引导程序再进入操作系统；本实验则观察 QEMU 复位代码、OpenSBI 和内核之间的交接。两者都体现分阶段建立运行环境并移交控制权，但具体架构、接口和加载机制不同。本次没有开展额外 PC 启动调试，不将该拓展计为实测任务。

## 六、实验总结与收获

### 6.1 对操作系统的理解：实验知识与 OS 原理的对应

| 重要知识点 | 本实验中的含义和实例 | 对应 OS 原理 | 二者的关系与差异 |
|------------|---------------------|-------------|------------------|
| 分阶段启动 | 复位代码转入固件，再到 `kern_entry` 和 `kern_init` | 系统引导与初始化 | 体现逐层建立运行环境；完整系统还需设备管理、内存管理、调度等后续初始化 |
| 地址与布局 | 链接基址 `0x80200000`，各节及符号的安排 | 程序内存布局、装载与地址空间 | 本实验关注链接地址与镜像放置的一致性；未实现一般进程的虚拟地址空间或按需装载 |
| 交叉编译和镜像 | 宿主机生成 RISC-V ELF 和原始镜像 | 编译、链接与程序装载 | ELF 可携带符号和调试信息，原始镜像不携带同等结构；本次由构建工具和 QEMU 完成这些环节 |
| 栈与调用约定 | 将 `sp` 设置为 `bootstacktop` 后进入 C 函数 | 执行上下文、函数调用和栈帧 | 为 C 运行提供基础；本次只有启动栈，没有实现不同进程的内核栈管理或上下文切换 |
| 静态对象初始化 | 使用 `edata`、`end` 界定 BSS 对应清零区间 | 程序运行环境及静态存储语义 | 内核需要自行承担普通程序运行库常做的初始化；当前构建清零长度为 0 |
| 特权服务接口 | 通过 `ecall` 请求旧版 SBI 控制台服务 | 特权级、受控入口和服务抽象 | 与系统调用都使用受控转移的思想；服务提供方、调用方和 ABI 不同，不能把 SBI 等同用户态系统调用 |
| 分层 I/O | 格式化输出、字符输出、SBI 封装分层 | 设备抽象和模块化设计 | 上层无需直接处理设备细节；本实验复用固件服务，没有实现完整终端驱动和中断输入 |
| 调试与可观察性 | 单步、断点、寄存器和反汇编互相印证 | 系统软件验证与故障定位 | 能检查特定路径是否达到预期；启动成功不代表所有潜在路径和异常场景均正确 |

### 6.2 OS 原理中重要但本实验尚未覆盖的知识

1. **进程与线程管理。** 未创建进程控制块，没有进程创建、退出、状态转换或多线程运行。
2. **CPU 调度与上下文切换。** 内核输出后循环，没有时间片调度、抢占或进程上下文保存恢复。
3. **虚拟内存与动态内存管理。** 没有实现页表管理、地址空间隔离、缺页异常处理、页面分配与回收。
4. **用户态程序与系统调用。** 没有装载用户程序，也没有实现用户态到内核的系统调用分发路径。
5. **中断与异常处理。** 本实验使用调试器观察运行，但未实现完整内核陷阱入口、时钟中断或外部中断处理框架。
6. **同步互斥与死锁。** 没有共享资源竞争场景，也没有实现锁、信号量或条件变量。
7. **文件系统与持久化存储。** 没有文件目录、磁盘块管理、缓存或系统崩溃后的恢复机制。
8. **多核协调与保护机制。** 虽然平台输出最大 Hart 数，但本次未验证多核启动、跨核同步及权限隔离。

这些内容并非不重要，而是依赖本实验建立的基本启动、执行环境和输出能力，需要在后续实验中逐步实现。

### 6.3 AI 协作开发的经验

1. **先对照任务要求，再判断是否完成。** 仅看到源码和编译产物不代表报告、练习解答和调试证据已经齐全。AI 的初步核对帮助识别了这些交付缺口。
2. **提供原始输出比描述“报错了”更有效。** GDB 明确返回不支持 `set logging enabled on`，据此改用本版本支持的 `set logging on`，比重复同一命令更有效。
3. **必须区分预期和实际。** `sp` 应变为 `0x80203000` 可以从指令解释，但未再次读取就不能声称日志已经显示这个结果。AI 整理报告时也应遵循同样原则。
4. **指导书提示需要结合实际配置。** 对 `watch *0x80200000` 的理解必须结合 Makefile 中的 loader 参数，不能把不同加载机制混用。
5. **源码、反汇编和寄存器需要一起看。** 一条 `la` 伪指令会展开为多条真实指令；结合源文件、`x/i` 和寄存器，才能解释为什么单步一次还停在同一源码行。
6. **完整保留问题和边界。** 重复 `display/i` 导致同一指令显示两次，是添加了两个自动显示项，不是 CPU 执行了两次；退出时的远程连接提示，也应与此前验证结果分开解释。

本次实验使我们能够将抽象的“启动操作系统”落实到具体地址、寄存器、指令和输出证据。后续应沿用这种验证方式，在扩展内核功能时同时明确前提、预期行为、实际结果及未覆盖范围。
